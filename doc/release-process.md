Garlicoin Core release process
==============================

This document describes the maintained release process for the Garlicoin Core 0.18.x line in this repository.

Release principles
------------------

Maintenance releases should remain narrowly scoped. They must not intentionally change Garlicoin consensus, proof of work, network identity, address formats, existing blockchain/datadir compatibility, or the Berkeley DB 4.8 wallet format unless such a change is explicitly planned and reviewed as a separate project.

The repository's current release path is GitHub Actions based. Historical Gitian instructions are no longer the maintained release procedure.

Prepare the release
-------------------

1. Update the version in `configure.ac` and confirm the generated package version is correct.
2. Add or update `doc/release-notes-X.Y.Z.md` with the user-visible changes, compatibility statement, supported platforms, and dependency baseline.
3. Update the root `README.md` when the new release becomes the maintained public version.
4. Keep dependency changes, build-system changes, and unrelated code changes out of the release-preparation commit unless they are part of the release itself.

Validation before tagging
-------------------------

All relevant pull-request checks should be green before the release is tagged. For the maintained x86_64 release set, validate at least:

- Linux build and tests;
- Windows x86_64 MinGW build;
- native macOS x86_64 build;
- wallet compatibility/smoke coverage relevant to the changes;
- cross-platform release packaging through `.github/workflows/release-validation-ci.yml`.

The release-validation workflow builds the pinned `depends` stack and checks the release artifacts for the expected target format. The native macOS release path additionally verifies Mach-O architecture, deployment target, and dynamic linkage.

When the final release commit is on `master`, run the release-validation workflow manually on that exact revision if the final merge changed the commit being validated.

Release artifacts
-----------------

The maintained release workflow produces the x86_64 release set:

- Linux archive;
- source archive;
- Windows x86_64 ZIP;
- Windows x86_64 NSIS installer;
- macOS x86_64 archive;
- macOS x86_64 DMG;
- SHA256 checksum files generated by the platform jobs.

Before publishing, verify that every expected file exists and that the filenames contain the intended version. Create a final combined checksum manifest for the files that will be attached to the GitHub release, for example on Linux:

```sh
sha256sum garlicoin-* > SHA256SUMS
```

Check the manifest itself before publishing it. Do not include temporary CI logs, dependency caches, or intermediate build products in the public release.

Tag and publish
---------------

1. Tag the exact validated release commit as `vX.Y.Z`.
2. Create the GitHub release for that tag.
3. Use `Garlicoin Core X.Y.Z - GRLC.eu Maintenance Release` as the release title for the maintained fork.
4. Attach only the validated release artifacts and the final `SHA256SUMS` manifest.
5. Copy the relevant contents of `doc/release-notes-X.Y.Z.md` into the GitHub release description or link to the file.
6. Verify the download links and checksums after publication.

After publication
-----------------

- Confirm the root `README.md` points to the current release and correct downloads.
- Keep the version-specific release notes in `doc/` as the durable repository record.
- Record any release-specific regression or follow-up work as a separate issue/maintenance change rather than silently altering an already published artifact.

Legacy build paths
------------------

The old Gitian release process and Linux-to-Darwin cross-build are not the maintained release path for the current Qt 5.15/OpenSSL 3.5 line. Their dedicated GitHub Actions workflows have been removed from the active workflow set. The supported macOS release build is native x86_64 through `.github/workflows/release-validation-ci.yml`.
